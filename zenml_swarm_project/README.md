# ZenML + MLflow + Optuna — Versioned Data & Models, Docker Swarm, GitHub CI

Same training pipeline as before (Breast Cancer dataset, RandomForest tuned by
Optuna, tracked in MLflow), extended with three things the previous project
didn't have:

1. **Data versioning** — DVC + git track exactly which dataset file fed each run.
2. **Model versioning** — every training run creates a new, immutable MLflow
   Model Registry version, auto-promoted to `champion` if it clears an
   accuracy threshold. Nothing is ever overwritten.
3. **Deployment** — a GitHub Actions workflow builds and publishes a Docker
   image on every push to `main`, and a `docker-stack.yml` file lets you run
   the whole thing as a Docker Swarm service.

**Tested before packaging:** the full pipeline (ingest → preprocess → train →
evaluate → register), the DVC versioning script, and the champion-loading
predictor all ran successfully end to end, including confirming a real
git-commit → data-hash → model-version chain. See "What was and wasn't
verified" at the bottom — Docker Swarm and the GitHub Actions workflow
specifically were **not** run in a live cluster/live repo, since that
requires infrastructure this environment doesn't have.

## STEP 1 — Install Prerequisites

- **Docker** (Desktop on Windows/Mac, or `docker.io` + `docker-compose-plugin` on Linux)
- **Git**
- A **GitHub account**, if you want the CI/publish workflow to run

Check:
```
docker --version
docker compose version
git --version
```

## STEP 2 — Unzip, Init Git, Init DVC

```
unzip zenml_swarm_project.zip
cd zenml_swarm_project
git init
git add .
git commit -m "initial commit"
```

Install DVC locally just to initialize it (or do this step inside the
container in Step 5 instead — either works):
```
pip install dvc
dvc init
git add .dvc .dvcignore
git commit -m "dvc init"
```

## STEP 3 — Push to GitHub

```
git remote add origin https://github.com/<your-username>/<your-repo>.git
git branch -M main
git push -u origin main
```

That's all that's needed for `.github/workflows/ci.yml` to start running —
it triggers automatically on every push to `main`, no extra secrets required
(`GITHUB_TOKEN` is provided automatically by GitHub Actions for pushing to
`ghcr.io`).

**What the workflow does:**
- `test-pipeline` job: installs dependencies, registers a ZenML stack, runs
  `python run_pipeline.py` as a smoke test, and runs `dvc add` on the dataset
  to confirm the data-versioning step works in a clean environment.
- `build-and-push-image` job (only on pushes to `main`, after tests pass):
  builds the Docker image and pushes it to
  `ghcr.io/<your-username>/<your-repo>`, tagged with both `latest` and the
  full git commit SHA.

## STEP 4 — Local Development (docker-compose)

For day-to-day iteration, use `docker-compose.yml` — it bind-mounts your
project folder, so code edits on your machine are instantly visible inside
the container:

```
docker compose build
docker compose up -d
docker compose exec zenml_app bash
```

You're now inside the container at `/app`.

## STEP 5 — Initialize ZenML and the Stack

Inside the container:
```
zenml init
zenml artifact-store register my_store --flavor=local
zenml orchestrator register my_orchestrator --flavor=local
zenml experiment-tracker register my_tracker --flavor=mlflow
zenml stack register my_stack -a my_store -o my_orchestrator -e my_tracker
zenml stack set my_stack
```

(mlflow integration is already installed in the image.)

---

## STEP 6 — Run the Pipeline

```
python run_pipeline.py
```

This runs ingest → preprocess → train (20 Optuna trials) → evaluate →
**register_model**. Expect output like:
```
Accuracy = 0.9649122807017544
...
Registered BreastCancerModel v1 — accuracy 0.9649 — promoted to champion
```

Every re-run creates a new registered version (v2, v3, ...). A version is
only tagged `champion` if its accuracy is ≥ 0.95 — otherwise it's tagged
`candidate` and the existing champion stays in place. Check
`steps/register_model.py` if you want to change that threshold.

---

## STEP 7 — Version the Dataset

After a pipeline run, `data/breast_cancer.csv` exists on disk. To snapshot it:
```
./scripts/version_data.sh "data: describe what changed"
```

This runs `dvc add` (hashes the CSV, writes `data/breast_cancer.csv.dvc`)
and commits that pointer file to git. The CSV itself stays out of git
(see `.gitignore`) — DVC tracks it separately in `.dvc/cache`, which you can
push to remote storage later with `dvc remote add` + `dvc push` if you want
the raw data backed up somewhere (S3, GCS, an internal server, etc. — not
configured here, since it depends on what storage you have access to).

Each MLflow run is tagged with the DVC hash that was active when it ran
(`data_version_md5`), so you can always trace a model version back to the
exact dataset version, and that dataset version back to the exact git commit
that introduced it.

## STEP 9 — Predict Using the Champion Model

```
python predictor.py
```

This searches the MLflow Model Registry for whichever version is currently
tagged `champion` and loads that one — not simply "the newest version" —
so a bad training run never gets served just because it happened most
recently.

## STEP 10 — Deploy with Docker Swarm

Swarm can't bind-mount your project folder (a container might get scheduled
onto a different machine than the one with your files), so `docker-stack.yml`
uses a pre-built image plus named volumes instead.

**Build (or pull a CI-built image) and initialize the swarm:**
```
docker build -t zenml_swarm_app:latest .
docker swarm init
```
(`docker swarm init` only needs to run once per machine; skip it if this
machine is already a swarm manager.)

**Deploy the stack:**
```
docker stack deploy -c docker-stack.yml zenml_stack
```

To use an image GitHub Actions already built and pushed, instead of a local
build:
```
IMAGE_NAME=ghcr.io/<your-username>/<your-repo>:main docker stack deploy -c docker-stack.yml zenml_stack
```

**Check it's running:**
```
docker service ls
docker service ps zenml_stack_zenml_app
```

**Get a shell in the running service** (same idea as `docker compose exec`,
just via the service name instead of a container name):
```
docker exec -it $(docker ps -q -f name=zenml_stack_zenml_app) bash
```
From here, Steps 5–9 work exactly the same way.

**Tear down:**
```
docker stack rm zenml_stack
```

### A note on multi-node Swarm

This `docker-stack.yml` is written to work correctly on a **single-node**
swarm (which is how most people first try Swarm — `docker swarm init` on
their own machine). On a real multi-node cluster, the named volumes
(`zenml_data`, `mlflow_data`, `project_data`) are still *local to whichever
node the container lands on* — Swarm doesn't replicate volume contents
across nodes by default. For genuine multi-node persistence you'd need a
shared volume driver (NFS, GlusterFS, a cloud block-store plugin, etc.),
which depends entirely on your infrastructure and isn't something a generic
template can set up for you.

## Quick Reference: The Three Versioning Layers

| What | How | Where to check it |
|---|---|---|
| Code | git commits | `git log`, tagged into every MLflow run as `git_commit` |
| Data | DVC hash of `breast_cancer.csv`, committed as a `.dvc` pointer | `data/breast_cancer.csv.dvc`, tagged into every MLflow run as `data_version_md5` |
| Model | MLflow Model Registry version + `stage` tag (`champion`/`candidate`/`previous_champion`) | MLflow UI → Models → BreastCancerModel |
| Image | Docker image tagged with git SHA, published by CI | `ghcr.io/<repo>:<sha>` |

Given a deployed model, you can walk this chain backwards: image tag → git
commit → exact code + exact data hash used to train it → MLflow run → all
hyperparameters Optuna tried.

## What Was and Wasn't Verified

**Actually run and confirmed working**, in this order, in a real (if
temporary) environment:
- Full pipeline run (ingest → preprocess → train → evaluate → register),
  twice, both times landing at ~96.5% accuracy.
- Model versioning: registry versions incremented correctly (v1 → v5 across
  test runs), `champion` tag applied above the 0.95 threshold.
- Data versioning: `dvc add` + `git commit` via `scripts/version_data.sh`,
  producing a real md5 hash.
- The full traceability chain: a real git commit hash and a real DVC data
  hash both showed up correctly as tags on a real MLflow run, and then on
  the resulting registered model version.
- `predictor.py` correctly finding and loading the champion version by tag
  (not just the newest version) and producing a prediction.

**Two real bugs this caught**, already fixed in the files you have:
- `train_model`'s multiple return values needed explicit `Annotated` tuple
  typing, or ZenML can't unpack them.
- `register_model`'s return type was declared `str` but MLflow's
  `ModelVersion.version` is actually an `int` — ZenML enforces step return
  types strictly and failed the step until this was corrected.

**Not run in this environment** (no Docker daemon, no live GitHub repo
available here): the actual `docker build`, `docker swarm init`/
`docker stack deploy` sequence, and the GitHub Actions workflow itself. The
YAML for `docker-compose.yml`, `docker-stack.yml`, and
`.github/workflows/ci.yml` was checked for valid syntax, and the commands
in this README match the Docker/Swarm/GitHub Actions documentation, but you
will be the first to actually execute that half of this project — if
something doesn't line up, it's most likely in that untested half.
